# Consciobite

Southeast Asia's first SKU-level carbon scoring and Digital Product Passport platform for food FMCG brands.

**Live demo:** [consciobite-app.onrender.com](https://consciobite-app.onrender.com) · **API docs:** [localhost:4000/api/docs](http://localhost:4000/api/docs) (dev only)

> The live demo runs on Render's free tier. First request after idle may take 30–60 seconds while the server cold-starts.

---

## The Problem

SGX-listed food manufacturers in Singapore face Scope 3 carbon reporting obligations under the SGX Sustainability Reporting framework. EU importers increasingly require Digital Product Passports (ESPR Regulation). No SEA-native platform exists to score food SKUs at the product level, track emissions across the supply chain, and generate structured carbon documentation for reporting workflows.

## What Consciobite Does

- **GreenGrade Algorithm** — Scores 550 food SKUs on a 0–10 scale using Gaussian Kernel Density Estimation across 7 supply-chain emission categories (Land Use Change, Animal Feed, Farm, Processing, Transport, Packaging, Retail). Uses variance-based feature importance, category-aware blending (60/40 category/global), and a sigmoid transform for resolution where products cluster.
- **Digital Product Passport API** — `GET /api/v1/passport/:productId` returns a structured JSON passport with GreenGrade score, percentile ranking, emission breakdown, data confidence tier, and carbon footprint per SKU. Structured to support EU ESPR and SGX Scope 3 reporting workflows.
- **Portfolio Scoring** — `POST /api/v1/portfolio/score` accepts up to 100 product IDs and returns the scored portfolio with category benchmarks, portfolio average, and highest/lowest performers. An ESG lead's entire range scored in one call.
- **Score Audit Trail** — Every score change is logged with product ID, old/new score, delta, methodology version, and timestamp. `GET /api/v1/audit/:productId` returns the full trail. Scores are generated by algorithm — when a brand asks "can you change my score," the audit log is the answer. (Application-level log today; tamper-evident storage is on the roadmap.)
- **Governance Layer** — Independent Advisory Panel oversight, manufacturer onboarding with non-contingent fee acknowledgement, public transparency dashboard with aggregate score-change statistics. Addresses the conflict of interest between listing fees and independent scoring.
- **Evidence Registry** — Every emission factor traces back to a registered literature source (Poore & Nemecek 2018, Our World in Data, Open Food Facts/Agribalyse, category estimates), each tagged with methodology, granularity, and a high/medium/low reliability rating. `GET /api/v1/evidence/product/:id` returns both the computed provenance and any explicit product-to-source links.
- **Community Evidence** — Signed-in users can submit citations against a product (`POST /api/products/:id/evidence`). Submissions land in a pending queue, are reviewed by an admin, and only surface publicly once approved. Submitted evidence never touches a score directly — it is review input, not an input to the algorithm.
- **Barcode Scanning** — Look up any product's GreenGrade by barcode, with Open Food Facts fallback for 2M+ products.
- **Anomaly Detection** — Mahalanobis distance from category centroids flags outliers beyond the chi-squared 95th percentile for 7 degrees of freedom.
- **ML Insights Layer** — Advisory endpoints (`/api/v1/ml/*`) backed by scikit-learn models trained offline on the catalog: greener-alternative similarity search, category classification for mis-tag detection, emissions estimation from partial data, and K-Means sustainability clusters.
- **Consumer App** — Product browse with search, category and GreenGrade tier filters; side-by-side comparison; per-product Digital Product Passport page; favorites; a carbon log with a configurable weekly goal and CSV export; and account data export/deletion.

> **Two engines, deliberately separate.** The GreenGrade score is produced by a hand-built statistical engine (Gaussian KDE + Mahalanobis anomaly detection in `backend/src/services/greengrade.js`). The ML Insights layer (`backend/src/services/mlInsights.js`) is a distinct, scikit-learn-derived engine trained offline in Python and evaluated in plain JS at runtime. ML predictions are advisory only — they never modify a product's category, emissions, or GreenGrade score, and never bypass the score audit trail. See [`ML_REPORT.md`](./ML_REPORT.md) for the full analysis.

## Quick Start

```bash
git clone https://github.com/J-Dheeraj/Consciobite-Application.git
cd Consciobite-Application/backend
cp .env.example .env   # Set JWT_SECRET
npm install && npm run dev
```

Backend runs at `http://localhost:4000`. API docs at `http://localhost:4000/api/docs`.

Frontend (separate terminal):

```bash
cd frontend && npm install && npm run dev
```

Frontend runs at `http://localhost:3000`.

The repo root holds tooling only (Prettier config and the Husky pre-commit hook). If you plan to commit, install it once so staged files are formatted automatically:

```bash
npm install   # in the repo root
```

### Docker

```bash
export JWT_SECRET=your-secret-here
docker compose up --build
```

### ML Model Training

The `/api/v1/ml/*` endpoints serve models trained offline with scikit-learn. The exported artifacts (`backend/src/data/ml_artifacts.json`) are committed, so no Python is needed to run the app. To retrain after changing the product catalog:

```bash
cd ml
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python greengrade_ml_analysis.py --data ../backend/src/data/products.json --out ../backend/src/data
```

Then restart the backend to load the new artifacts.

## Methodology

GreenGrade v3.0 uses Gaussian Kernel Density Estimation with Silverman bandwidth selection to score products relative to their category peers and the global catalog. Data sourced from Poore & Nemecek (2018) lifecycle assessments, Our World in Data, and Open Food Facts/Agribalyse.

Full technical specification: [`METHODOLOGY.md`](./METHODOLOGY.md)

## Security

JWT authentication with HS256 pinning · CSRF double-submit on mutating routes · bcrypt (cost 12) · rate limiting (API, auth, scan) · account lockout (5 attempts) · declarative input validation · Helmet headers · non-root Docker · CORS restricted origins · Swagger disabled in production · admin routes via `requireAdmin` middleware.
